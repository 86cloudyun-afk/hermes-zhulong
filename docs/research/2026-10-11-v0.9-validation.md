## Protected runner 与实际 Docker 边界

原内联脚本审批问题由新的可信入口处理：部署启动前创建只读 runner，以完整 SHA 纳入保护，私有 profile 只预授权 `python3 /root/.hermes/cache/generated/zhulong-work-runner.py` 这一条精确命令。它读取并执行同一份候选代码与冻结输入字节，不包含参考答案；完整业务验收、原生轨迹审计和宿主 deny/hardline 守卫继续生效。其他动作仍由宿主权限约束。

实际探测复现固定镜像的 `/root` tmpfs 默认 mode=700，导致 uid 1000 无法遍历到已授权 runner。修复将该 mount 明确设置为 `rw,exec,size=1g,mode=711` 并严格检查实际挂载选项；目录仍属 uid 0，worker 只能穿越，不能列举或写入 `/root`。缓存/来源仍只读，worker user、capability drop、无网络和只读根边界保留。该权限修复经独立限定审查 Ready，50 项定向测试通过，0 Critical / 0 Important；审查者未运行 Docker/付费模型。

唯一计为正式通过的 probe 为 `trusted-runner-offline-20261011-r3-root711-verified`，保留 `probe.py`、`report.json` 与 `probe.log`：**exit 0、ok=true、owned_containers_absent=true、外部 LLM 调用 0、gateway 启动 0**。实际精确命令前台执行返回 0，code/input/output 哈希匹配；来源和 generated-cache 挂载只读，runner/来源写入被拒，控制代码、provider key 和 Docker socket 不可见。完整摘要和三个文件的 SHA-256 见脱敏证据。

此前 `trusted-runner-offline-20261011-r3` 的失败、`...-diagnostic` 的诊断失败以及 `...-root711-experiment` 的清理竞态记录均保留；实验中的局部执行成功不计为正式 probe 通过。后续独立清理确认另记，不覆盖原失败/不完整收据。
