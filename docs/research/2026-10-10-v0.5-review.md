## Critical

### R1 — A read-only source file overlay does not protect its writable ancestors or existing hard-link aliases

Locations: `runtime_policy.py:51-59`, `runtime_policy.py:64-65`, `runtime_policy.py:163`, `runtime_supervisor.py:68-70`; boundary probe `scripts/runtime_probe.py:65-68`.

The deployment accepts source files anywhere below the writable work root and overlays just each file as read-only. A nested source's containing directory remains mutable through the work bind. Replacing/renaming that parent can change the host-visible source pathname while the existing read-only overlay still refers to the old topology. Existing hard-link aliases likewise are not rejected. This breaks the promised OS-enforced immutability of source facts and can feed model-authored facts into later host planning. The probe only attempts opening one exact source path for write, so its success does not establish the stronger integrity property. The parent reported the nested-parent case before this review; source inspection confirms the missing protection. I did not reproduce it with Docker.

**Required fix/validation:** The proposed restriction to regular, single-link files directly under the work root is a sound bounded remedy for the stated worker threat model. Reject nested paths, symlink/nonregular topology and `st_nlink != 1`; inspect original/lexical paths as needed so normalization does not silently hide a rejected topology. Preserve or explicitly revalidate the intended resolved work/source topology (device/inode and parent relationships), and check it during supervision before admission/relaunch. Pure unit tests should cover nested source rejection, symlinks, nonregular sources, existing hard links, and topology drift after initialization. A top-level source file is an overlay mount point beneath the work mount point, so the mutable intermediate-parent route is removed. Periodic detection alone is not a substitute for the structural restriction. Any final native validation of this remedy is for the parent under its authorized workflow; this reviewer did not execute it. Update docs to explain the restriction and qualify the old probe evidence.

## Important

### R2 — Gateway process-group descendants survive when the leader exits

Locations: `runtime_supervisor.py:119-137`, especially `130-135`.

Shutdown signals the group only if `self.child.poll() is None`, then waits only for the direct child. If the leader has already exited, the entire group is skipped. If the leader exits promptly after SIGINT while another group member ignores it, the direct-child wait returns successfully and no escalation occurs. Surviving descendants can retain descriptors/locks or other resources, and the supervisor can start another gateway or report stopped while its old group remains. The documented outer process manager is for supervisor/host failure; it does not repair ordinary internal restart cycles while the supervisor stays alive.

**Required validation:** Add provider-free subprocess fixtures with a leader that spawns a same-group descendant and exits, and a leader that exits on SIGINT while the descendant ignores it. Assert bounded group cleanup before relaunch or stopped status, preservation of unrelated groups, and eventual inherited-lock release. Track/check owned group lifetime independently of leader liveness; handle group-disappearance races without turning normal shutdown into an error.

### R3 — Operator stop requests can be overwritten during preflight/restart

Locations: `scripts/runtime.py:33-37`; `runtime_supervisor.py:114-117`, `150-156`, `178-181`.

The CLI writes `stopping` into the same boot control record that the supervisor uses for its internal shutdown and next startup. A stop during failure-driven shutdown is indistinguishable from the supervisor's own stopping record; after cleanup, only `stop_event` is checked and the next loop writes a fresh starting record. The operator request is lost and another gateway can start. During initial checking there may be no boot at all; during subsequent preflight the CLI can target the previous boot, which is also overwritten. Thus a successful CLI stop does not reliably stop a deployment in a recovery transition.

**Required validation:** Use deterministic fixture barriers for checking/preflight, failure cleanup, and the interval before fresh-boot publication. Request stop in each phase and assert no subsequent gateway launch and a truthful stopped outcome. Keep operator intent separate from internally generated lifecycle states, or provide an equivalent race-safe protocol scoped to the active supervisor invocation. Ensure an intentional later `run` has defined semantics after a prior stop.

### R4 — Mutable work/config validation can disable the status and stop commands

Locations: `scripts/runtime.py:29-36`; `runtime_policy.py:135-140`, `33-42`; `autonomy_checks.py:45-50`, `91-92`, `113`.

`status` and `stop` call `load_manifest(verify=False)`, but that still requires the work directory to exist and fully normalizes/validates current autonomy sources and output contracts. For example, an authorized worker can replace its output pathname with a symlink outside work; contract normalization then raises `outside_workspace`. The operator cannot publish stop or inspect persisted service status through the supported CLI. Missing/renamed work directories and damaged configuration have the same effect. These are precisely the states in which emergency observation and shutdown must remain usable. Stronger source topology checks must not make this dependency worse.

**Required validation:** After creating/starting a temporary fixture deployment, introduce an output symlink outside work, move the work directory, and corrupt the autonomy configuration in separate tests. `status` should still provide control-plane diagnostics and `stop` should still deliver the stop request. Resolve trusted deployment identity/control paths using minimal validation for these actions; keep full execution validation on `check`/`run`.

### R5 — Status reports persisted running state as though it were current

Location: `scripts/runtime.py:31-32`; relevant producer `runtime_supervisor.py:61-64`, `169-177`.

`status` prints saved service and plugin records without checking process identity, freshness, or matching boot/PID. After supervisor death it can continue returning `service.state = running`; after child death the plugin snapshot can also remain running. A wrong-boot health record is returned without qualification. The existing duplicate/orphan fixture verifies lock behavior, but does not verify the status command. Moreover, the supervisor's status timestamp is not refreshed in the running loop, so simply expiring that timestamp would incorrectly mark a healthy long-running process stale.

**Required validation:** Add CLI tests for a live deployment, supervisor death with a live orphan, both processes dead, stale plugin health, and wrong-boot health. Return a clearly derived live/stale/orphaned/unknown state and retain historical records only as labeled last observations. Use credible process identity/freshness evidence, accounting for PID reuse and the current non-heartbeating status record. Do not infer clean per-run settlement from process disappearance.

### R6 — Failed/timed-out native preflight has no reliable ownership cleanup

Locations: `runtime_supervisor.py:81-89`, `119-120`, `150-152`, `183-187`; probe cleanup `scripts/runtime_probe.py:90-93`.

Preflight is a synchronous `subprocess.run` that can create a Docker worker. On timeout Python kills the direct probe process, so its `finally` cleanup cannot be relied on and subprocess descendants are not owned as a separate group. The supervisor's exception handler calls `shutdown_child`, which immediately returns because no gateway was created; its scoped worker cleanup is therefore skipped. A timed-out probe or other failure after worker creation can leave a labeled container/resource behind while reporting blocked. The normal post-preflight cleanup only runs when preflight succeeds.

**Required validation:** With injected/mock worker cleanup and provider-free probe fixtures, verify cleanup on preflight exception, timeout, interruption, and cancellation before gateway creation; include a probe descendant that outlives its leader. Own and terminate the probe group on failure, and always attempt deployment-scoped worker cleanup after acquiring ownership, even without a gateway child. Verify that duplicate-lock rejection never cleans another live invocation's workers. Cleanup failure should remain visible in status rather than being silently discarded. No Docker reproduction is necessary to establish the missing exception path.

## Minor

### M1 — Health parsing is not consistently schema-safe or finite-number-safe

Locations: `runtime_supervisor.py:39-48`, `108-112`, `172-176`; `runtime_channel.py:27-32`.

Some malformed shapes are handled, but a list/null `progress` or `status` can raise before the readiness exception guard. `ready_body` similarly assumes `readiness` is a mapping. The progress-age test accepts nonfinite/future timestamps: NaN makes the `>` comparison false, and positive infinity never ages out. Ordinary `atomic_json` publication forbids NaN, so this is malformed/corrupt-record hardening under the stated trusted-control-plane model, not a demonstrated model escape.

**Validation:** Table-driven tests for nested null/list/scalar values, booleans masquerading as numbers, NaN/infinity, and future/stale timestamps; all must fail closed with a stable reason and bounded lifecycle behavior. Consider central parsing of the full health schema.

### M2 — Actual tmpfs limits are not checked despite the documented inspect guarantee

Locations: `runtime_policy.py:106-115`; `docs/deployment/supervised-runtime.md` resource row.

Worker inspection only requires a truthy `HostConfig.Tmpfs`; it does not validate required mount paths/options/size bounds. MemorySwap is configured but not checked either. The pinned native code currently supplies explicit tmpfs sizes (`tools/environments/docker.py` default security args and nonpersistent mounts), and the trusted generated configuration fixes memory/swap, so this is a verification completeness issue rather than evidence that the measured worker was unbounded.

**Validation/ruling:** Add inspect-fixture failures for missing/extra/unbounded/wrong-sized tmpfs and swap drift, or explicitly narrow the assertion/documentation to the fields actually inspected. Do not claim all resource settings are checked from the current boolean test.
