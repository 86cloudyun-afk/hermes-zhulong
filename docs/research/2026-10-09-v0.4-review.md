## Important findings

### I1 — A pre-claim snapshot can settle a newer live submission and permit another run (P1)

**Locations:** `autonomy.py:207`, `autonomy.py:215`, `autonomy.py:219`; `autonomy_store.py:186`, `autonomy_store.py:198`, `autonomy_store.py:220`.

`tick()` reads goals before acquiring ownership and passes that old goal/submission directly to `_reconcile()`. Acquiring a new valid lease does not refresh the snapshot or compare its submission ID. `record_admission()` accepts any submission belonging to the goal, while `transition()` and `finish()` settle the goal's **current** submission. Ownership fencing therefore does not fence which submission the reconciliation concerns.

**Concrete reproduction:** Use two controllers sharing the ledger, `safe_retry=true`, `max_active=1`. Start submission 1. Controller A reads its recovery snapshot and pauses before claim. Controller B reconciles submission 1 as a verified failure, then dispatches submission 2. Resume A: it acquires the now-current goal lease but reconciles its old submission-1 snapshot. The reproduced outcome is `attempts=2`, `state=ready`, and current submission 2 `settled=true` although its remote status is still queued/running. The next tick starts submission 3: three admissions total, with submission 2 still running despite `max_active=1`. See `stale_snapshot_after_A` / `stale_snapshot_next_tick` in the reproduction output.

**Consequence:** Multiple supported host instances can prematurely free in-flight capacity, dispatch overlapping attempts, lose tracking of the real execution, and attach terminal conclusions to the wrong attempt. This defeats the central durable-recovery guarantee.

**Fix:** Refresh the goal under the newly acquired lease before deciding the action; make the claimed snapshot/state/submission identity part of the transaction contract. Require every attempt-affecting admission, transition and finish operation to compare the expected current submission ID, in addition to owner/generation/lease checks. Add a deterministic two-controller test for this exact interleaving and assert that the live second submission retains its slot.

### I2 — Overlapping file and argv contracts can both claim one run's artifact (P1)

**Locations:** `autonomy_store.py:168`–`172`; `autonomy.py:149`, `autonomy.py:158`–`160`.

The verification-resource guard only compares exact strings: a file contract protects its `path`, whereas an argv contract protects its `cwd`. It does not detect that the file lies within that cwd. Thus the intended cross-goal evidence exclusion is incomplete even without adversarial filesystem behavior.

**Concrete reproduction:** Configure `max_active=2`, a code contract `file_contains(work/result.txt, "done")`, and a research argv contract running in `work` that succeeds iff `result.txt` exists. Both have a failing acceptance baseline and `require_change=true`. Dispatch both before the artifact exists. Only the file-contract run creates `result.txt`; the other run produces nothing and reports completed. Both independent checks now pass, both goals become `succeeded`, and the self-model records **two verified successes from one producing run**. See `overlapping_argv_file_evidence` (`calls=2`, `runs_that_produced_artifact=1`, `verified_successes=2`).

**Consequence:** The self-model awards capability evidence to an execution that contributed no new result, contrary to the artifact provenance requirement and the ledger ruling that resource accounting prevents cross-goal credit.

**Fix:** Represent conflict scopes explicitly. At minimum, conservatively exclude overlap between an argv cwd tree and descendant file contracts, and overlapping argv directory trees. Arbitrary argv may inspect outside cwd; either declare/validate its evidence resources or conservatively serialize it within the relevant authorized scope. Recheck before dispatch so an artifact created by the earlier run becomes `already_satisfied`, or use submission-bound receipts where available. Add the mixed file/argv regression case.

### I3 — Temporary auxiliary-budget exhaustion permanently disables unchanged sources (P2)

**Locations:** `autonomy.py:27`–`28`, `autonomy.py:87`–`104`; `autonomy_store.py:244`, `autonomy_store.py:247`, `autonomy_store.py:257`.

A source attempt is consumed before planning. `LLMPlanner` raises `auxiliary_budget_exhausted` or `planner_unavailable` before making any model request, but `_synthesize()` treats these as ordinary failed planning attempts. After the configured maximum, `claim_source()` refuses that fingerprint forever, even after the budget or runtime prerequisite becomes available.

**Concrete reproduction:** Return `PlannerError('auxiliary_budget_exhausted')` for three source claims spaced more than the 60-second cooldown. Restore the working planner and advance into the next day. A further tick makes no restored-planner call and produces no goal; source state remains `failed, attempts=3`. See `budget_recovered_next_day` (`goals=0`, `restored_planner_calls=0`). The same pre-call error is emitted by the actual budget guard at line 28.

**Consequence:** Ordinary daily cap exhaustion silently strands newly observed work indefinitely. Replenishing the shared budget, resuming, or restarting with working credentials does not recover it; changing source content or editing internal state is required.

**Fix:** Distinguish unavailable prerequisites from an executed invalid/failed planning attempt. Retain a retryable blocked state with an appropriate recovery condition (such as budget day/cap availability or runtime availability), without consuming the content-failure allowance before a model request is made. Preserve bounded retries for actual invalid plans. Test exhausted budget followed by restored budget on unchanged facts.

### I4 — Source planning leases are never renewed during permitted long calls (P2)

**Locations:** `autonomy.py:87`, `autonomy.py:91`–`104`; `autonomy_store.py:114`–`117`, `autonomy_store.py:256`.

Goal execution has `_heartbeat()`, but source planning and baseline capture do not. Config validation permits any positive `lease_seconds`, including values shorter than the planner's permitted 45-second request or a configured argv check. Once the source lease expires, `create_goal()` rejects the valid result and `complete_source()` also refuses the update. `_synthesize()` ignores both refusal paths, and subsequent retries ultimately exhaust the source allowance.

**Concrete reproduction:** Set valid `lease_seconds=1` and use a planner returning a valid candidate after a **real 1.15-second sleep**, with `Controller.clock=time.time`. Three ticks make three valid planner calls but create zero goals. The source remains in an expired `planning` state with `attempts=3`; a fourth tick cannot claim it. This reproduction uses actual elapsed time, not an instantaneous fake-clock jump; see `valid_slow_planning`.

**Consequence:** Valid configurations silently discard successful planning work and can permanently stop autonomous progress. Multiple processes can also begin duplicate synthesis once the unrenewed source lease expires, wasting the shared auxiliary budget.

**Fix:** Add source lease renewal/heartbeat across planning and all baseline captures, with ownership/fingerprint fencing and explicit handling of ownership loss. Alternatively enforce a lease minimum that covers the full bounded operation, though renewal handles long configured checks more robustly. Test real elapsed time past an initial lease while renewal is active, and competing ownership takeover.

### I5 — Approval-blocked work is retried without a changed prerequisite or safe-retry contract (P2)

**Locations:** `autonomy.py:143`–`145`, `autonomy.py:156`–`157`, `autonomy.py:183`–`185`, `autonomy.py:223`.

After `waiting_for_approval`, the controller stops the run and correctly marks it blocked. Once the host reports cancellation, it records a settled `blocked/runtime_requires_approval`. On the next tick the generic blocked-goal dispatch path immediately changes it to ready and prepares another submission. Neither a changed approval prerequisite nor `safe_retry=true` is required.

**Concrete reproduction:** With the default `safe_retry=false`, run `queued → waiting_for_approval → cancelled`, ticking through each state. Immediately before the next tick, the goal is `blocked`, reason `runtime_requires_approval`, attempts 1. The next tick starts a second external run and changes attempts to 2 with no configuration or facts changed. See `approval_block_retries`.

**Consequence:** Unattended approval-required work repeatedly consumes attempts and dispatch budget and may repeat actions preceding the approval gate. The recorded blocked state does not enforce its recovery condition. The existing approval test checks only the first stop, so misses the redispatch.

**Fix:** Persist and enforce a specific recovery condition for approval-blocked goals. A terminal stop response should settle tracking, not authorize a new submission. Resume only after the relevant execution-policy prerequisite actually changes and any retry safety requirements are satisfied. Add a full stop-to-terminal-to-next-tick regression with `safe_retry=false`.

### I6 — Optional autonomy storage failure removes legacy commands and tools (P2)

**Location:** `__init__.py:187` (before registrations at lines 196–207 and cleanup at lines 209–221).

Creating the new ledger and refreshing/exporting the self-model occurs outside the autonomy initialization exception boundary and before every command/tool registration. A storage or export failure therefore jumps to the outer registration catch, even when autonomy is disabled.

**Concrete reproduction:** In a clean temporary profile, make `zhulong/autonomy.db` a directory and register the plugin normally. SQLite cannot open the new ledger. The real registration result is 11 hooks, **zero tools, zero commands, zero unload callbacks**. No Ledger mock is used in the final reproduction; only warning logging is silenced. See `optional_ledger_failure`.

**Consequence:** Failure of the new optional subsystem disables previously working calibration/prediction tools, `/zhulong`, reflection scheduling and cleanup registration. This violates the intended isolation and compatibility of the control layer; old observation hooks surviving does not preserve the old interfaces.

**Fix:** Register/retain legacy commands, tools and cleanup independently of new-ledger/model initialization. Catch new storage/export failures within the optional subsystem boundary and expose an unavailable reason for new interfaces, while allowing old functionality and S4 to continue. Test both ledger-open failure and model-export failure with autonomy disabled.

## Strengths

- Atomic SQLite admission and budget reservations, immutable submission fields, owner/generation/expiry checks, and persisted cancellation intent are substantial improvements. The existing separate-process budget/admission and process-death tests are useful.
- Pending submission recovery precedes new-work budgets and pause handling. The final-attempt/zero-budget/lost-response test verifies reuse of the original submission rather than allocating a new attempt.
- The public Runs adapter freezes request and session affinity, checks endpoint/profile/identity version, rejects redirects, bounds response bytes, sanitizes returned metadata, and requires durable idempotency capabilities. It does not expose auth values or raw response bodies in errors.
- `interrupted` remains uncertain occupancy, and late artifact appearance does not authorize replacement execution. This is appropriately conservative given the pinned public protocol's quiescence limitations.
- The verifier reads bounded output while the child runs, uses a monotonic deadline and process-group cleanup, rejects nonregular/oversized files and out-of-root symlinks, and reports unavailable checks as unknown. Existing verifier tests pass.
- Goal truth has a unique final-truth index, attempt evidence is stored separately, and the model distinguishes first-attempt from eventual success. Existing-artifact tests and the narrow real-model validation are clearly separated from wider capability claims.
- Documentation accurately limits the delivered scope: no consciousness claim, no OS sandbox claim, no global currency/token cap, and only one real local code contract tested against DeepSeek.

5. **Old artifacts / receipts / retry success:** ordinary existing artifacts and repeated final truth are handled; I2 violates cross-run artifact credit for overlapping mixed contracts. First and eventual success are otherwise separated in the inspected model code/tests.

Correct updates to `api_identity_version` are a deployment obligation and cannot be inferred from environment-variable names.
